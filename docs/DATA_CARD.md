## 2. What is in it

Customer comments about smartphones collected by the authors from a large Vietnamese e-commerce website. Each comment is annotated with (aspect, sentiment) pairs.

| Split | Reviews | No aspect label¹ | No usable date² | Avg. labels / review | Median length (chars) | Max length |
|---|---:|---:|---:|---:|---:|---:|
| train | 7,786 | 115 | 856 (11.0%) | 3.07 | 129 | 846 |
| dev | 1,112 | 18 | 115 (10.3%) | 2.98 | 126 | 613 |
| test | 2,224 | 37 | 251 (11.3%) | 3.02 | 129 | 850 |

¹ Only the `{OTHERS}` token, e.g. pure questions ("Sản phẩm không có tai nghe hả bạn?").
² Relative dates such as "2 tuần trước" with no anchor.

Columns: `index, comment, n_star, date_time, label`. Absolute dates range from Dec 2016 to Aug 2020. No review exceeds the API's 2,000-character limit.

| **STORAGE** | 18 | 6 | 3 | **27** |

Observations:
- **Heavy imbalance across aspects**: STORAGE is 50× rarer than GENERAL.
- **PRICE is mostly neutral**: customers often state a price without judging it, which is a likely source of LLM confusion between neutral and positive.
- **FEATURES skews negative**: complaints about software/features dominate.
- Neutral is the minority class for almost every aspect.

## 3. Quirks handled by the loader (`src/review_insight/data/visfd.py`)

| Quirk | Handling |
|---|---|
| Label syntax `{ASPECT#Polarity};` with capitalized polarity | Mapped to domain enums (`Sentiment.POSITIVE`, ...) |
| `{OTHERS}` token, which **co-occurs with real aspects in ~20% of rows** | Ignored. It means "also talks about something outside the 10 aspects", not "no aspect". *An early spec draft got this wrong; corrected after profiling.* |
| Dates are day-first; ~11% are relative | Parsed as day-first; relative or invalid dates become `None` |
| Files start with a UTF-8 BOM | Read with `utf-8-sig` |
| Comments contain line breaks | Read with the `csv` module (`newline=""`); text kept verbatim |
| Malformed labels | None found, but the loader fails loudly with file and row index if one appears |

## 4. Evaluation samples (`evals/data/samples.json`)

Fixed, committed **indices** (seed 42), generated by `scripts/make_samples.py`. They are stratified by star rating with largest-remainder allocation.

| Sample | Drawn from | Size | Purpose |
|---|---|---:|---|
| `test_500` | test | 500 | Main comparison of all configurations |
| `smoke_50` | `test_500` | 50 | CI eval gate on prompt/LLM changes |
| `dev_100` | dev | 100 | Prompt iteration (the test split is never used for tuning) |

The star distribution of `test_500` matches the test split within 0.1 percentage points. Aspect shares match within about 3 points, **except**:

### Known limitations and decisions

1. **STORAGE is nearly absent from samples** (2 reviews in `test_500`, 0 in `smoke_50`; 27 in the full test split).
   - *Decision:* keep samples representative; do **not** oversample rare aspects, because that would bias the primary micro-averaged metric.
   - Per-aspect F1 is reported from the **full test split**, always with support counts. Aspects with support < 30 are flagged as not conclusive.
2. **`smoke_50` deviates from the population** (e.g. PERFORMANCE 38% vs 52.7%), which is expected sampling noise at n = 50.
   - *Decision (deferred to T22):* the CI gate compares two prompt versions **on the same 50 reviews** (paired), which cancels most of this noise. The gate threshold (currently 0.03 pair-F1) will be set from a **paired bootstrap** on real predictions. If noise still exceeds it, the smoke set grows to 100 or the threshold is relaxed accordingly.
3. **The official train/dev/test split is never re-split**, so results remain comparable with the paper (Bi-LSTM: ~84% aspect F1, ~63% sentiment F1).
4. **Domain and time:** smartphone reviews from 2016–2020 on one retailer. Performance on other product categories or on current slang is not measured.
5. **Annotation:** the gold labels come from the authors' annotation scheme. Disagreements between the LLM and gold labels are inspected manually in the error analysis (T20) before being called model errors.

## 5. Where review text is sent

The raw files stay in `data/raw/` (gitignored). Review text leaves the machine in three places,
all private to this project and all within research use:

| Destination | What | Why |
|---|---|---|
| Google Gemini API | Each review sent for analysis | The task itself. On the free tier, Google may use prompts to improve its products (see `docs/GEMINI.md`) |
| `evals/.cache/` (local, gitignored) | Model responses, which can echo review text | Re-running evals for free |
| Langfuse Cloud (private project) | Traces of real model calls; datasets `visfd-<split>` with the review and its gold labels | Tracing, prompt management, dataset runs (T9) |

Rules: Langfuse datasets and traces are never made public (no public trace links, no shared
datasets); the git repository never contains review text, only indices and aggregate metrics.
